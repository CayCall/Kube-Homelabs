1. Containers & Docker

Kubernetes doesn't run "apps". It runs containers. So that's where we start.

The problem containers solve

"It works on my machine" happens because an app depends on a specific OS, libraries and settings. A container packages the app together with everything it needs, so it runs the same everywhere.

A container is not a virtual machine. A VM fakes an entire computer, with its own kernel, and takes minutes to boot. A container is just a normal process on the host that has been given its own isolated view of the filesystem, network and process list. It shares the host's kernel, so it starts in milliseconds.

   Virtual machines                      Containers
┌──────┐ ┌──────┐ ┌──────┐         ┌──────┐ ┌──────┐ ┌──────┐
│ App  │ │ App  │ │ App  │         │ App  │ │ App  │ │ App  │
│ Libs │ │ Libs │ │ Libs │         │ Libs │ │ Libs │ │ Libs │
│Guest │ │Guest │ │Guest │         └──────┘ └──────┘ └──────┘
│  OS  │ │  OS  │ │  OS  │         ┌──────────────────────────┐
└──────┘ └──────┘ └──────┘         │  Container runtime       │
┌──────────────────────────┐       ├──────────────────────────┤
│       Hypervisor         │       │  Host OS kernel (shared) │
└──────────────────────────┘       └──────────────────────────┘

Image vs container

Image

A read-only template: a snapshot of a filesystem plus a start command. Like a recipe, or a class in programming.

Container

A running instance of an image. Like the dish cooked from the recipe. You can run many containers from one image.

Registry

Where images are stored and downloaded from: Docker Hub (docker.io), quay.io, ghcr.io, dhi.io.

An image name looks like registry/repository:tag, e.g. quay.io/argoproj/argocd:v3.5.3. If you leave off the registry, Docker Hub is assumed (nginx = docker.io/library/nginx).

Why :latest is risky

A tag is just a label that can be moved. nginx:latest today and nginx:latest next month can be completely different software. Your nginx.yaml and Kali Dockerfile both use moving tags. Production setups pin a version (nginx:1.29) or even a digest (@sha256:…), which can never change. Your vendored Argo CD chart pins digests in its Chart.yaml.

A Dockerfile: your Kali "VM", line by line

In your repo

app-roots/KaliLinux-VirtualMachine/Dockerfile. Despite the folder name, this is a container, not a VM.

FROM kalilinux/kali-rolling                 # start from someone else's image
RUN apt-get update && apt-get install -y \  # each RUN adds a "layer" to the image
    openssh-server openssh-client \
    && rm -rf /var/lib/apt/lists/*          # clean up in the same layer to keep it small
RUN mkdir -p /run/sshd
RUN echo 'PermitRootLogin yes' >> /etc/ssh/sshd_config
RUN echo 'PasswordAuthentication yes' >> /etc/ssh/sshd_config
RUN ssh-keygen -A                           # generate the server's host keys
RUN echo 'root:…' | chpasswd                # ⚠ password baked into the image + git
EXPOSE 22 443 80                            # documentation only, doesn't open anything
CMD ["/usr/sbin/sshd", "-D"]                # the process the container runs

Key idea: a container lives exactly as long as its main process (CMD). sshd -D runs in the foreground forever, so the container stays up.

docker compose: running it with settings

services:
  kali:
    build: .                 # build the Dockerfile in this folder
    container_name: kali-vm
    ports:
      - "2222:22"            # HOST:CONTAINER, so localhost:2222 → container port 22
      - "8080:80"
      - "8000:443"
    restart: unless-stopped  # come back automatically when Docker restarts

"2222:22" is the single most important thing to read correctly: left = your PC, right = inside the container. Kubernetes uses the same idea in port-forwarding.

Check yourself

What's the difference between an image and a container?

An image is the read-only template; a container is a running instance of it. One image → many containers.

In "8000:443", which number is on your PC?

8000. Left is the host, right is the container. Browsing to https://localhost:8000 reaches port 443 inside kali-vm.

Why don't your nginx pods show up in docker ps?

They run inside the kind-control-plane container, managed by containerd. Docker on Windows only sees the outer container.

2. What Kubernetes Is

Kubernetes is a system that keeps reality matching what you asked for, forever.

The one idea: desired state

You don't tell Kubernetes "start 2 nginx containers" (an instruction). You tell it "there should be 2 nginx containers" (a desired state). Kubernetes then runs a control loop, constantly:

     ┌───────────────────────────────────────────┐
     │                                           │
     ▼                                           │
 1. OBSERVE  ──▶  2. COMPARE  ──▶  3. ACT  ──────┘
 "1 pod running"   "want 2, have 1"  "start 1 more"

It's like a thermostat: you set 21°C, and it keeps working until the room is 21°C, and keeps checking after. Kill a pod, and the loop notices and makes a new one. This is called reconciliation, and it's the reason Kubernetes "self-heals".

You describe desired state in YAML files (declarative), and submit them with kubectl apply.

Anatomy of every Kubernetes object

In your repo

nginx.yaml, the first thing you ever deployed.

apiVersion: apps/v1        # which API group/version defines this type
kind: Deployment           # what type of object
metadata:
  name: nginx              # its name (unique per kind, per namespace)
spec:                      # ← DESIRED state: what YOU want
  replicas: 2
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:latest
          ports:
            - containerPort: 80
# status:                  # ← ACTUAL state: Kubernetes fills this in. You never write it.

spec vs status is the desired-state idea in code. The gap between them is what controllers work to close.

The parts of a cluster

┌──────────────────────── CONTROL PLANE (the brain) ────────────────────────┐
│                                                                           │
│  kube-apiserver ◀── everything talks ONLY to this (kubectl, Argo CD, …)   │
│       │                                                                   │
│       ├── etcd                   the database: stores all desired state   │
│       ├── kube-scheduler         picks which node a new pod runs on       │
│       └── kube-controller-manager runs the control loops (Deployments…)   │
└───────────────────────────────────────────────────────────────────────────┘
┌──────────────────────── WORKER NODE (the muscle) ─────────────────────────┐
│  kubelet          node agent: "API says run pod X here", makes it happen  │
│  containerd       actually starts/stops containers                        │
│  kube-proxy       programs networking rules for Services                  │
│  CNI (kindnet)    gives every pod an IP and connects them                 │
└───────────────────────────────────────────────────────────────────────────┘
In your cluster

kind squashes both boxes into one node, kind-control-plane. Every part above is a real pod you can see in the kube-system namespace: kube-apiserver-kind-control-plane, etcd-kind-control-plane, kube-scheduler-…, kube-controller-manager-…, kube-proxy-…, kindnet-…, plus coredns (cluster DNS). Real clusters have 3 control-plane nodes and many workers.

What happens when you kubectl apply -f nginx.yaml

  1. kubectl sends the YAML to the API server over HTTPS.
  2. The API server validates it and saves it in etcd. That's it, nothing is running yet.
  3. The Deployment controller notices a new Deployment and creates a ReplicaSet, which creates 2 Pod objects (still just records).
  4. The scheduler sees 2 pods with no node, and assigns them to a node.
  5. The kubelet on that node sees pods assigned to it and tells containerd to pull nginx:latest and start it.
  6. kubelet reports back; status is updated. kubectl get pods shows Running.

Notice nobody gives orders directly; every component just watches the API server and does its one job.

Lab: meet your cluster

  1. Your one node, with details: 
    kubectl get nodes -o wide
  2. The control-plane components, running as pods: 
    kubectl get pods -n kube-system
  3. Every type of object your cluster understands (notice applications, added by Argo CD): 
    kubectl api-resources

Check yourself

What's the difference between spec and status?

spec is what you want (you write it). status is what actually exists (Kubernetes writes it). Controllers work to make status match spec.

Which component does kubectl talk to?

Only the kube-apiserver. Nothing talks to etcd or kubelets directly.

Which component decides what node a pod runs on?

The kube-scheduler. In your one-node cluster the answer is always kind-control-plane.

3. kubectl, Contexts & kubeconfig

kubectl is your remote control. kubeconfig tells it which TV to point at.

kubeconfig: the address book

kubectl reads %USERPROFILE%\.kube\config. It has three lists:

SectionHoldsYours
clustersAPI server address + the CA certificate to trustkind-kind → https://127.0.0.1:53551
docker-desktop → https://127.0.0.1:53022
usersCredentials (here: client certificates)kind-kind, docker-desktop
contextsA named pair: cluster + user + default namespaceNebula, docker-desktop

Exactly one context is current. Every kubectl command goes to the current context unless you add --context.

Gotchas from your setup
  • Context names are case-sensitive. Yours is Nebula; docs/argo-cd-deploy.md says nebula.
  • The current context was docker-desktop, not your kind cluster. Always check with kubectl config current-context when something looks wrong.

Real-world lesson: the AVG x509 error

kubectl connects over HTTPS. The kubeconfig contains your cluster's own Certificate Authority (CA), and kubectl will only accept a server certificate signed by that CA. That's how it knows it's talking to your real cluster and not an impostor.

kubectl ──HTTPS──▶ [ AVG Web Shield ] ──HTTPS──▶ kube-apiserver
                    re-signs the cert
                    with "AVG Untrusted Root"
kubectl: "This isn't signed by my cluster's CA. Refusing." → x509 error

AVG's "HTTPS scanning" is a deliberate man-in-the-middle, and kubectl correctly refused it. Lesson: x509 / certificate errors are usually about who is answering, not about Kubernetes being broken. Fix: add an exception for 127.0.0.1/localhost in AVG Web Shield.

Workaround while it's broken: run kubectl inside the node, where AVG can't see it:

docker exec kind-control-plane kubectl --kubeconfig /etc/kubernetes/admin.conf get pods -A

The verbs you'll use 90% of the time

CommandWhat it does
kubectl get <type>List objects. Add -o wide, -o yaml, -w (watch), --show-labels
kubectl describe <type> <name>Human-readable details + Events (your #1 debugging tool)
kubectl apply -f file.yamlMake the cluster match this file (create or update)
kubectl delete -f file.yamlDelete what the file describes
kubectl logs <pod>Container output. -f to follow, --previous for the last crash
kubectl exec -it <pod> -- shShell inside a container

Scope flags: -n argocd = one namespace. -A = all namespaces. No flag = the context's default namespace (usually default).

Declarative vs imperative

kubectl create deployment web --image=nginx is imperative: quick, but the only record is in the cluster. kubectl apply -f web.yaml is declarative: the file is the record, it can live in git, and Argo CD can apply it for you. Use imperative for experiments, declarative for anything you want to keep.

Check yourself

What are the three parts of a context?

A cluster, a user, and (optionally) a default namespace.

You run kubectl get pods and see nothing, but you know nginx is running. Name two possible reasons.

Wrong context (e.g. docker-desktop), or wrong namespace (it lives in default and you're looking elsewhere). Try kubectl get pods -A.

What did the x509 error actually mean?

The certificate kubectl received wasn't signed by your cluster's CA, because AVG replaced it. kubectl refused to trust it.

4. Pods

The smallest thing Kubernetes runs. Important to understand, but you'll rarely create one by hand.

What a pod is

A pod is a wrapper around one (usually) or more containers that:

  • share one IP address (containers in a pod talk via localhost),
  • can share volumes (folders),
  • are always scheduled together on the same node.

Multi-container pods are for tightly coupled helpers ("sidecars"), e.g. a log shipper next to an app. Most pods have one container.

Pods are disposable

A pod is never repaired or moved. If it dies or its node dies, it's gone, and something else must create a new pod (with a new name and a new IP). That "something else" is a controller like a Deployment, which is the next lesson.

A minimal pod

apiVersion: v1
kind: Pod
metadata:
  name: hello
  labels:
    app: hello
spec:
  containers:
    - name: web
      image: nginx:1.29
      ports:
        - containerPort: 80

Pod lifecycle

PhaseMeaning
PendingAccepted, but not running yet: waiting for a node, or pulling the image
RunningBound to a node, at least one container running
SucceededAll containers exited with code 0 (normal for batch Jobs)
FailedA container exited with an error and won't be restarted

The RESTARTS column counts container restarts inside the same pod. Your pods show 3 to 5 restarts. That's not a bug: it's every time Docker Desktop (and so the whole node) was restarted.

In your cluster: the bare kali pod

default/kali is a pod created by hand (probably kubectl run kali --image=kalilinux/kali-rolling -it -- /bin/bash) on 2026-09-21. It has no controller and no YAML in git. If you delete it, nothing brings it back, and there's no record of how it was made. That's exactly why you'd normally use a Deployment, and keep the YAML in git.

Lab: a pod's whole life

  1. Create a pod and watch it start (Ctrl+C to stop watching): 
    kubectl run hello --image=nginx:1.29 -n playground
kubectl get pods -n playground -w
    You'll see ContainerCreating → Running.
  2. Read its details. Scroll down to Events at the bottom: scheduling, pulling, starting. 
    kubectl describe pod hello -n playground
  3. See its IP (from the pod network, 10.244.x.x) and node: 
    kubectl get pod hello -n playground -o wide
  4. Read its logs and look inside:

Check yourself

Two containers in the same pod: how do they talk to each other?

Over localhost. They share the pod's network namespace and IP.

A pod's node crashes. Does Kubernetes move the pod?

No. Pods are never moved. A controller (like a Deployment) notices it's missing and creates a new pod elsewhere. A bare pod just disappears.

Where's the first place to look when a pod is stuck in Pending?

kubectl describe pod <name>, specifically the Events section at the bottom.

5. Deployments & ReplicaSets

How you actually run apps: self-healing, scaling, and zero-downtime updates.

The chain of ownership

Deployment  nginx                 "I want 2 replicas of THIS pod template,
   │                               and I manage updates between versions"
   ▼
ReplicaSet  nginx-59c4c87bc6      "I keep exactly 2 pods of ONE version alive"
   │                               (the hash = a fingerprint of the template)
   ├──▶ Pod  nginx-59c4c87bc6-gh4zr
   └──▶ Pod  nginx-59c4c87bc6-smgd2

Those are your real pod names. The naming pattern tells you who owns what: <deployment>-<replicaset-hash>-<random>.

What the Deployment gives you

Self-healing

Pod deleted or crashed? The ReplicaSet makes a new one immediately.

Scaling

Change replicas and pods are added or removed.

Rolling updates

Change the image and pods are replaced a few at a time, so the app never fully goes down.

Rollback

Old ReplicaSets are kept, so you can go back to the previous version in one command.

The selector ↔ labels contract

spec:
  selector:
    matchLabels:
      app: nginx        # "the pods I own are the ones labeled app=nginx"
  template:
    metadata:
      labels:
        app: nginx      # "pods I create get labeled app=nginx"  ← MUST match

If these don't match, Kubernetes rejects the Deployment. This label-matching idea comes back with Services in Lesson 7.

In your repo

Both nginx.yaml (2 replicas) and app-roots/values.yaml (3 replicas) define a Deployment called nginx in the same namespace. The cluster is running 2, so nginx.yaml was applied. If you ever apply values.yaml, it won't create a second app; it will update the same one to 3 replicas. Same kind + name + namespace = same object.

Other controllers in your cluster

KindUse it forExample in your cluster

StatefulSetPods that need a stable identity/name and their own disk (databases)argocd-application-controller (pod is always -0)

  1. Create a Deployment from YAML (paste the whole block into PowerShell): 
    @'

kind: Deployment

  name: web
  namespace: playground

  replicas: 3
  selector:
    matchLabels:
      app: web

'@ | kubectl apply -f -
  2. See the whole chain: 
    kubectl get deploy,rs,pods -n playground
  3. Self-healing. Open a second PowerShell window and watch, then delete a pod from the first window (use a real name from the list): 
    # window 2
kubectl get pods -n playground -w
# window 1
kubectl delete pod -n playground <one-of-the-web-pod-names>
    A replacement appears within a second or two. Compare that with the bare pod in Lesson 4.
  4. Scale: 
    kubectl scale deployment web -n playground --replicas=5
kubectl get pods -n playground
  5. Rolling update to a new image version, and watch it roll: 
    kubectl set image deployment/web nginx=nginx:1.29 -n playground

Check yourself

Deployment, ReplicaSet, Pod: which one actually creates pods?

The ReplicaSet. The Deployment creates and manages ReplicaSets, one per version of the pod template.

Why does a rolling update leave an old ReplicaSet with 0 pods?

So kubectl rollout undo can scale it back up instantly.

Which controller would you use for a database? For a log agent on every node?

StatefulSet for the database; DaemonSet for the per-node agent.

6. Namespaces, Labels & Selectors

Namespaces are folders. Labels are tags. Selectors are searches over tags.

Namespaces

A namespace groups related objects. Names only need to be unique within a namespace, so playground/web and default/web can coexist.

Your namespaceContains
defaultWhere things go if you don't say: nginx, kali
argocdAll of Argo CD
kube-systemKubernetes' own components. Don't touch.
kube-public, kube-node-leaseInternal housekeeping
local-path-storageThe storage provisioner (Lesson 9)
playgroundYour lab sandbox

Deleting a namespace deletes everything inside it. Great for cleanup, dangerous with the wrong name.

Not a security wall

By default, pods in different namespaces can still talk to each other freely. Isolation needs RBAC (who can do what) and NetworkPolicies (who can talk to whom) on top.

Some objects aren't in any namespace (cluster-scoped): Nodes, Namespaces themselves, StorageClasses, ClusterRoles, CRDs. See them with kubectl api-resources --namespaced=false.

Labels and selectors

A label is a key/value tag on any object: app: nginx, env: dev. A selector finds objects by label. This is how Kubernetes wires things together without hard-coding names:

Deployment  selector: app=web ──┐
                                ├──▶  Pod  labels: app=web   ✓
Service     selector: app=web ──┘     Pod  labels: app=web   ✓
                                      Pod  labels: app=other ✗

Pods come and go with random names, but their labels stay predictable, so labels are how everything finds them.

In your cluster

The Argo CD Helm chart uses the standard recommended labels: app.kubernetes.io/name, app.kubernetes.io/instance: argocd, app.kubernetes.io/part-of: argocd, app.kubernetes.io/managed-by: Helm, helm.sh/chart: argo-cd-10.9.2. That last label is how we found out which chart is really deployed.

Annotations look similar but aren't for selecting. They hold extra info for tools (e.g. kubectl.kubernetes.io/last-applied-configuration).

Lab: labels in action

  1. Show labels and filter by them: 
    kubectl get pods -n playground --show-labels

  2. Add a label to one pod, then select it: 
    kubectl label pod -n playground <one-web-pod> tier=frontend

Check yourself

Can two Deployments both be called web?

Yes, if they're in different namespaces.

Why did relabeling a pod make the Deployment create a new one?

The ReplicaSet counts pods matching its selector. The relabeled pod no longer matched, so it counted one too few and created another.

Does a namespace stop pods from talking to pods in other namespaces?

No. You'd need NetworkPolicies for that.

7. Networking & Services

How traffic finds pods that keep changing their IPs, and how you reach them from Windows.

Rule 1: every pod gets its own IP

The CNI plugin (kindnet in your cluster) gives each pod an IP from the pod CIDR (10.244.0.0/16). Any pod can reach any other pod by IP directly, with no port mapping. But pod IPs change every time a pod is recreated, so you can't rely on them.

Rule 2: Services give a stable address

A Service is a stable virtual IP + DNS name in front of a set of pods, chosen by a label selector. It load-balances across whichever matching pods are healthy right now.

                    Service "web"  (ClusterIP 10.96.x.x, port 80)
 client pod ──▶     selector: app=web
                       │  kube-proxy rules spread traffic
           ┌───────────┼───────────┐
           ▼           ▼           ▼
     Pod 10.244.0.20  Pod .21    Pod .22      (targetPort 80)

Service IPs come from the service CIDR (10.96.0.0/12). That's why all your Services are 10.96.something.

The ports, untangled

FieldWhereMeaning
containerPortPod specThe port the app listens on (mostly documentation)
targetPortServiceWhich port on the pod to send traffic to
portServiceThe port the Service itself listens on
nodePortService (NodePort type)A port 30000–32767 opened on every node

Service types

TypeReachable fromNotes

NodePortNode IP + port 30000–32767In kind, the "node" is a container, so you also need extraPortMappings when creating the cluster
LoadBalancerAn external IP from the cloudNeeds a cloud, or a tool like MetalLB / cloud-provider-kind locally
Headless (clusterIP: None)DNS returns pod IPs directlyUsed by StatefulSets

Rule 3: DNS names

CoreDNS gives every Service a name: <service>.<namespace>.svc.cluster.local. From a pod in the same namespace, just web works. From another namespace, use web.playground. Argo CD's server finds Redis at argocd-redis:6379 this way.

Why not just connect to a pod's IP?

Pod IPs change whenever a pod is replaced. A Service's IP and DNS name stay the same.

How does a Service know which pods to send traffic to?

8. ConfigMaps & Secrets

Keep configuration out of the image, so one image works everywhere.

ConfigMaps

A ConfigMap stores non-secret key/value data or whole files. Pods consume it two ways:

  • as environment variables (env / envFrom), or
  • as files in a mounted volume, where each key becomes a file.
This very website

In cluster mode, these HTML/CSS/JS files live in a ConfigMap called kb-site-…, mounted into nginx at /usr/share/nginx/html. The nginx image is stock, and the content comes from config. See How This Site Runs.

Secrets

A Secret is structured like a ConfigMap but meant for sensitive data: passwords, tokens, keys. Kubernetes treats it a bit more carefully (it's not printed in describe, can be restricted with RBAC, and can be encrypted at rest if configured).

base64 is NOT encryption

Secret values are only base64-encoded. Anyone who can read the Secret can decode it in one command. That's exactly how your forgotten Argo CD password was recovered:

kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath="{.data.password}" | base64 -d

So: never commit a Secret YAML to git. Lesson 12 covers how to do it safely.

Secret types you'll meet

TypeForYour repo
OpaqueAnything (default)argocd-secret, argocd-initial-admin-secret
kubernetes.io/dockerconfigjsonLogging in to a private registry to pull imagesapp-roots/create-secret.sh (Docker Hub, placeholder)
kubernetes.io/tlsTLS certificate + keyArgo CD can use one for its UI

Lab: config without rebuilding

  1. Create a ConfigMap and a Secret: 
    kubectl create configmap app-settings -n playground --from-literal=GREETING=hello --from-literal=COLOR=blue
kubectl create secret generic app-secret -n playground --from-literal=API_KEY=super-secret-123
  2. Prove the Secret is only encoded: 
    kubectl get secret app-secret -n playground -o yaml
kubectl get secret app-secret -n playground -o jsonpath="{.data.API_KEY}" | base64 -d
    (No base64 in PowerShell? Use Git Bash, or [Text.Encoding]::UTF8.GetString([Convert]::FromBase64String("…")).)
  3. Run a pod that reads both as environment variables: 
    @'

Check yourself

Is a Kubernetes Secret encrypted?

Not by default. It's base64-encoded, which anyone can reverse. Protection comes from RBAC, optional encryption-at-rest, and keeping it out of git.

You change a ConfigMap used as env vars. Do running pods see the new value?

No. Env vars are read when the container starts, so you must restart the pods (kubectl rollout restart deployment/…). Mounted files do update, after a short delay.

9. Storage

Containers forget everything when they restart. Volumes are how data survives.

Volume types, from shortest-lived to longest

VolumeLives as long asUse for
Container filesystemThe containerNothing you care about
emptyDirThe podScratch space shared between containers in a pod
configMap / secretThe ConfigMap/SecretConfig files (like this site)
PersistentVolumeClaimUntil you delete the claimDatabases, uploads, anything real

PV, PVC, StorageClass

Pod ──uses──▶ PersistentVolumeClaim  "I need 1Gi, read-write"   (you write this)
                     │ bound to
                     ▼
              PersistentVolume       an actual piece of disk     (created for you…)
                     ▲
                     │ provisioned by
              StorageClass "standard" → rancher.io/local-path    (…by this)

You only write the PVC. The StorageClass automatically creates a matching PV ("dynamic provisioning").

In your cluster
  • StorageClass standard (default) uses local-path-provisioner, which creates a folder on the node's disk.
  • VOLUMEBINDINGMODE: WaitForFirstConsumer: a PVC stays Pending until a pod actually uses it. That's normal, not an error.
  • RECLAIMPOLICY: Delete: delete the PVC and the data is deleted too.
  • The "node's disk" is inside the kind-control-plane container. Deleting the kind cluster deletes all PVC data.
  • No PVCs exist yet. Argo CD keeps its state in Kubernetes objects and git, not on disk.

Lab: data that survives a pod

  1. Create a claim, and notice it stays Pending: 
    @'
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: notes
  namespace: playground
spec:
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 100Mi
'@ | kubectl apply -f -
kubectl get pvc -n playground
  2. A pod that writes to it: 
    @'
apiVersion: v1
kind: Pod
metadata:
  name: writer
  namespace: playground
spec:
  containers:
    - name: sh
      image: busybox:1.36
      command: ["sh", "-c", "date >> /data/log.txt; cat /data/log.txt; sleep 3600"]
      volumeMounts:
        - name: notes
          mountPath: /data
  volumes:
    - name: notes
      persistentVolumeClaim:
        claimName: notes
'@ | kubectl apply -f -
kubectl get pvc,pv -n playground
    Now the PVC is Bound and a PV exists.
  3. Delete the pod, recreate it (re-run the step 2 block), and check the log: 
    kubectl delete pod writer -n playground
kubectl logs writer -n playground
    Two timestamps: the data outlived the first pod.

Check yourself

Which of PV, PVC, StorageClass do you normally write?

Just the PVC. The StorageClass provisions the PV.

Your PVC is Pending. Broken?

Probably not. With WaitForFirstConsumer, it binds once a pod uses it.

What happens to PVC data if you run kind delete cluster?

It's gone. It lives inside the node container.

10. Helm

A package manager for Kubernetes: install a whole app (dozens of YAML files) with one command.

Why Helm exists

Argo CD alone is ~60 Kubernetes objects. Writing those by hand, then tweaking them per environment, is painful. Helm packages them as a chart: YAML templates with blanks, plus a values.yaml that fills the blanks.

templates/deployment.yaml          values.yaml            rendered YAML
  replicas: {{ .Values.replicas }}  +  replicas: 2    ──▶   replicas: 2
  image: {{ .Values.image }}           image: nginx:1.29    image: nginx:1.29

The vocabulary

TermMeaningYours
ChartThe package (templates + default values + Chart.yaml)app-roots/argocd/argocd-chart
ValuesSettings that fill the templates; you override defaults with your own fileChart defaults only so far
ReleaseOne installed copy of a chart, with a nameargocd in namespace argocd
RevisionEach install/upgrade bumps it; you can roll backRevision 1
RepositoryWhere charts are downloaded fromoci://dhi.io, argo-helm
Dependency / subchartA chart inside a chartredis-chart (as redis-ha), haproxy-chart, both off unless enabled

Core commands

helm list -A                                  # every release in the cluster
helm install <release> <chart> -n <ns> -f my-values.yaml
helm upgrade <release> <chart> -n <ns> -f my-values.yaml
helm rollback <release> <revision> -n <ns>
helm uninstall <release> -n <ns>
helm template <release> <chart>              # render YAML WITHOUT installing (great for learning)
helm show values <chart>                      # every setting you can change
helm get values <release> -n <ns>             # what YOU overrode
Mystery solved: which chart is deployed?

Your repo contains the Docker Hardened Images chart (argocd-chart 10.9.1, appVersion 3.5.2, images from dhi.io). But the running release says helm.sh/chart: argo-cd-10.9.2, app v3.5.3, images from quay.io. So the install came from the upstream argo-helm chart, not from the folder. That's why docs/information.md saw a version mismatch.

To manage it from the repo going forward, pick one source, save your settings in a real values file (e.g. app-roots/argocd/values-homelab.yaml), and always helm upgrade with it. Or, better, let Argo CD manage itself (next lesson).

Naming trap

app-roots/values.yaml is not Helm values. It's a plain nginx Deployment manifest. Helm values files contain settings, never apiVersion/kind.

Lab: look under Helm's hood

  1. Your releases and what was overridden: 
    helm list -A
helm get values argocd -n argocd
helm history argocd -n argocd
  2. Render the vendored chart without installing and look at the output: 
    helm template test app-roots\argocd\argocd-chart -n argocd | Select-Object -First 80
  3. Find the setting for the number of argocd-server replicas: 
    helm show values app-roots\argocd\argocd-chart | Select-String -Pattern "replicas" | Select-Object -First 10
  4. See exactly which manifests Helm deployed for the live release: 
    helm get manifest argocd -n argocd | Select-String "^kind:" | Group-Object | Sort-Object Count -Descending

Check yourself

Chart vs release?

A chart is the package; a release is one installed instance of it with a name (you could install the same chart twice as two releases).

How do you preview what Helm would create, without touching the cluster?

helm template.

How can you tell which chart version a running app came from?

helm list, or the helm.sh/chart label on its objects.

11. GitOps & Argo CD

Stop running kubectl apply. Commit to git, and let the cluster pull.

GitOps in one picture

  You ──git push──▶ GitHub: CayCall/Kube-Homelabs  (the SOURCE OF TRUTH)
                         │
                         │  Argo CD polls every ~3 min (or webhook)
                         ▼
                 ┌──── Argo CD ────┐
                 │ desired (git)   │──compare──▶ live (cluster)
                 │                 │
                 │ OutOfSync? ─────┼──▶ apply the difference
                 └─────────────────┘

It's Lesson 2's reconciliation loop again, one level up: Kubernetes makes the cluster match etcd, and Argo CD makes etcd match git.

Audit trail

Every change is a commit: who, what, when, why.

Easy rollback

git revert, and the cluster follows.

Drift detection

Someone ran kubectl edit? Argo CD shows it as OutOfSync, and can undo it.

Rebuild anything

New cluster + Argo CD + your repo = everything back.

Argo CD's parts (all running in your argocd namespace)

ComponentJob

The Application: Argo CD's unit of work

Argo CD adds new object types to Kubernetes using CRDs (Custom Resource Definitions). The main one is Application: "take this path in this git repo, and keep it deployed to this namespace."

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: knowledge-base
  namespace: argocd                # Applications always live in Argo CD's namespace
spec:
  project: default
  source:
    repoURL: https://github.com/CayCall/Kube-Homelabs.git
    targetRevision: main           # branch, tag, or commit
    path: knowledge-base           # folder in the repo (Kustomize detected automatically)
  destination:
    server: https://kubernetes.default.svc   # "this same cluster"
    namespace: knowledge-base
  syncPolicy:
    automated:
      prune: true                  # delete things removed from git
      selfHeal: true               # undo manual changes
    syncOptions:
      - CreateNamespace=true

Healthy / Progressing / DegradedIs the app actually working?

In GitOps, does your laptop push changes to the cluster?

No. You push to git; Argo CD (inside the cluster) pulls from git and applies.

12. Managing Secrets Properly

GitOps says "everything in git". Security says "no passwords in git". Here's how to satisfy both.

First: two different kinds of secret

Human loginsMachine secrets
ExamplesArgo CD admin, Kali root, GitHub, Azure portalRepo tokens, registry pull secrets, database passwords
Who reads itYouPods
Store inA password manager (Bitwarden, 1Password)A secrets system (below)

Option A: Sealed Secrets (simple, all local)

your PC:   Secret YAML ──kubeseal (public key)──▶ SealedSecret YAML ──▶ git ✓ safe
cluster:   SealedSecret ──controller (private key)──▶ normal Secret ──▶ pod

Only your cluster's controller can decrypt. Catch: back up the controller's private key. If you delete the kind cluster without it, your sealed files can't be decrypted anymore.

Option B: External Secrets Operator + Azure Key Vault (industry pattern)

Azure Key Vault (secret lives HERE, never in git)
        ▲
        │ ESO authenticates (service principal) and fetches
        │
cluster: ExternalSecret YAML in git ("get 'argocd-repo-pat' from the vault")
        └──▶ ESO creates a normal Secret ──▶ pod

Git only holds a pointer. Survives cluster deletion, costs cents per month, and the exact same setup works with AWS Secrets Manager or HashiCorp Vault. Catch: the service principal's credentials are the one secret you still have to put in by hand (the "secret zero" problem).

Sealed SecretsESO + Azure Key Vault
CostFree~cents/month
SetupLowMedium
Survives cluster rebuildOnly if you backed up the keyYes
Career valueGoodHigh (standard on AKS/EKS)
Things to fix in your repo
  • Kali root password is in the Dockerfile, and therefore in git history forever. If the GitHub repo is public, treat it as public. Best fix: SSH key login with PasswordAuthentication no. Then there's no password at all.
  • argocd-initial-admin-secret still exists. After changing the admin password, Argo CD's docs say to delete it: kubectl -n argocd delete secret argocd-initial-admin-secret.
  • create-secret.sh takes a password on the command line, so it ends up in your shell history. Prefer --from-file, or one of the options above.

Lab: find secrets that shouldn't be in git

  1. Search the repo for likely secrets (run in Git Bash or PowerShell with git): 
    git grep -n -i -E "password|passwd|secret|token|chpasswd"
  2. Check whether a secret was ever committed, even if it's been deleted since: 
    git log -p -S "chpasswd" --oneline
    This is why "I deleted it later" doesn't help: git history keeps everything.
  3. List the Secrets in your cluster (names only, not values): 
    kubectl get secrets -A

Check yourself

Where should your Argo CD admin password live?

In a password manager. It's a human login, not something pods read.

Is it safe to commit a SealedSecret to a public repo?

Yes, that's the point. Only the cluster's private key can decrypt it.

You remove a password from a file and commit. Is it gone?

No, it's still in git history. Rotate (change) the password.

How This Site Runs

This website is itself a small Kubernetes app, so it doubles as a worked example.

Two ways to open it

Local modeCluster mode
Command.\knowledge-base\serve.ps1.\knowledge-base\deploy.ps1
URLhttp://localhost:8090http://localhost:8091
NeedsPythonRunning cluster + working kubectl

Cluster mode, piece by piece

knowledge-base/site/*.html|css|js
        │  kustomization.yaml → configMapGenerator
        ▼
ConfigMap  kb-site-<hash>     ← the hash changes whenever the content changes
        │  mounted as files at /usr/share/nginx/html
        ▼
Deployment kb  (nginx:1.29-alpine, 1 replica, read-only, probes)
        │  selected by app.kubernetes.io/name=knowledge-base
        ▼
Service    kb  (ClusterIP :80)
        │  kubectl port-forward svc/kb -n knowledge-base 8091:80
        ▼
http://localhost:8091

Concepts this uses (and where they're taught)

  • Namespace knowledge-base: Lesson 6
  • Deployment with labels, a selector, resource limits and readiness/liveness probes: Lesson 5
  • ConfigMap mounted as a volume: Lesson 8
  • ClusterIP Service + port-forward: Lesson 7
  • Kustomize: built into kubectl (kubectl apply -k). It bundles several YAML files and generates the ConfigMap from the site files.
  • GitOps via argocd/application.yaml: Lesson 11
Why the ConfigMap name has a hash

Pods don't restart when a ConfigMap changes. Kustomize names the ConfigMap after a hash of its content (kb-site-7g2k9…) and updates the Deployment to point at the new name. A changed Deployment means a rolling update, so new content rolls out automatically.

Editing the site

  1. Lessons are <article> blocks in site/index.html. The sidebar builds itself from each article's data-title and data-group (learn or repo).
  2. Building blocks: <div class="callout tip|warn|repo">, <section class="lab">, <section class="quiz"> with <details>, <pre class="diagram">.
  3. Preview with local mode, then re-run deploy.ps1 (or merge to main once Argo CD manages it).
  4. Keep the three site files under ~250 KB in total: kubectl apply stores a copy of each object in an annotation, which has a size limit.

Lab: deploy this site yourself

  1. See what Kustomize generates, without applying anything: 
    kubectl kustomize knowledge-base | Select-String "^kind:|^  name:"
  2. Apply it and watch it come up: 
    kubectl apply -k knowledge-base
kubectl get all,configmap -n knowledge-base
  3. Open it: 
    kubectl port-forward svc/kb -n knowledge-base 8091:80
    http://localhost:8091. Your progress checkmarks won't carry over: each address has its own browser storage.
  4. Change a word in site/index.html, apply again, and watch a rolling update triggered purely by content: 
    kubectl apply -k knowledge-base
kubectl get configmap,rs -n knowledge-base
